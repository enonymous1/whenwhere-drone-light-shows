# Staff Review — WhenWhere Drone Light Shows

**Scope:** `index.html` (1,084 lines, ~68 KB, single-file page),
`tools/build.py` (759 lines, the generator — moved into the repo
2026-11-12 as part of the Pages workflow),
`README.md`, `LICENSE`, `assets/` (7 JPEGs).
**Date:** 2026-11-12. **Reviewer role:** staff engineer / maintainer.
**Method:** read every line of the generator and the built page, verified
each finding against the code, and implemented the fixes marked **Fixed**
below — then rebuilt and re-verified (see [Verification](#verification)).

## Verdict

This is a well-built single-page site with a genuinely good interactive
core: the Formation Studio's geometry is correct, the fleet counts are
honest, the form degrades gracefully to demo mode, and accessibility is
better than most marketing pages (real buttons, `role="status"`, reduced
motion handled). The page itself is ready to deploy.

The weakness is not the page — it is the **build pipeline and the lack of
any safety net around it**. The page is generated by a 759-line Python
script that string-patches a frozen upload, and until this review there
was no test, no syntax check, and no validation that a successful build
had produced a working page. Several of the fixes below are things the
build was silently doing wrong (dead passes, dead functions, stale
comments) that no one could have caught, because nothing checked.

## 1. Best Practices & Code Quality

### 1.1 Dead code — the build was doing work it threw away (Fixed)

**`fix_studio_shapes` was entirely dead.** It made 7 assertion-checked
replacements against the old `heartPath`/draw-based shapes — and
`fix_studio_sampling`'s splice then replaced that whole region with the
new contour engine. The pass existed only as a maintenance trap: if the
original upload's glass code ever changed, the build would fail on a
patch whose output was discarded anyway. **Removed the function and its
call.**

The same applied to parts of `fix_fleet` and `fix_js`:

- `fix_fleet`'s star/finale `draw:` entries, its stride-thinning block,
  its `step = 8` rep, and its `wordPoints` target reps — all on text the
  splice discards. **Removed.** (The `sample()` signature rep stays: it
  is the splice anchor.)
- `fix_js`'s `step = 20 → 12` rep — same story. **Removed.**
- `import sys` was unused. **Removed.**

**In the shipped page:** `thinMaximin()` (~25 lines, the old farthest-point
thinner) and `sample()` (the old raster sampler) were defined and never
called. Both **removed** from the studio engine. `thinUniform()` and
`resample()` are the live ones; they are used.

### 1.2 Error handling — mostly good, with one honest gap

What is good and should be kept:

- `rep()` asserts every replacement (`expected 1x …, found Nx`). A missed
  anchor fails loud instead of shipping the old text. This is the best
  habit in the codebase.
- The form validates every field before submit, and the accumulation
  pattern is correct: `ok = mark('f-name', …) && ok` evaluates `mark()`
  first, so all fields get marked even after an earlier failure.
- `getImageData` is wrapped in try/catch and degrades to an empty shape
  rather than throwing (canvas tainting).
- The `no-cors` form post has a `.catch()` path that shows the
  copy/download fallback.

**The gap — `fetch` success is assumed, not observed.** With
`mode: 'no-cors'` the browser returns an opaque response for any status,
including 404: the `.then()` fires and the page shows "Thank you" even
if the form URL is wrong or an entry ID is mistyped, and nothing arrives.
There is no way to detect this from the page — that is the cost of
`no-cors`. **Documented** in the README's Google Form section (verify
with a test inquiry). Do not "fix" this by switching to `cors` mode:
Google Forms does not send CORS headers, so that would break submission
entirely. The correct mitigations are the test inquiry and, later, a
server-side endpoint that returns a real status.

Smaller items:

- `wordPoints` had a retry fallback (`if (cp.length < 6)`) that re-ran
  the **identical** render on a fresh canvas — it could never change the
  outcome, because the canvas was already empty and the inputs were the
  same. **Removed.**
- `dateInput.min` is set from `toISOString()`, which is UTC. Near
  midnight local time the minimum date can land a day late (e.g. 23:00
  EST → the UTC date is tomorrow). Fix: format the local date instead of
  slicing an ISO string.
- The studio IIFE does `document.getElementById('sky').getContext('2d')`
  with no null check. If the canvas is ever absent, the throw kills the
  whole `<script>` block — the studio, the package shortcuts, *and* the
  form all fail to wire up, because they share one script tag. Add a guard
  that returns early if the canvas or its context is missing.
- The clipboard fallback creates a visible `<textarea>` and appends it to
  the body — it can flash on screen for a frame. Position it off-screen
  (`position: fixed; opacity: 0`) as the standard recipe does.
- Clearing the custom-word input leaves the last word on screen: the
  `input` handler only calls `setFormation` when `w.trim()` is non-empty.
  Decide the intended behavior (clear to a blank sky, or keep the last
  word) and make it explicit.

### 1.3 Performance

**Fixed — `wordPoints` allocated a full-stage canvas per character per
keystroke.** Every `input` event created one 900×520 canvas per character
(~2 MB each, plus a `getImageData` copy) — ~10 MB of allocation for typing
"LOVE". Each glyph is now rastered on a tight canvas just big enough for
it (`measureText` width + 16 px, `size × 1.5` tall) and translated back by
the same offset. **Verified pixel-identical** against the old output
(LOVE / E + J / 2027 screenshots match the pre-change renders dot for
dot; counts unchanged).

**Not changed, recommended:**

- `draw()` sets `ctx.shadowBlur = 12` and a shadow color per drone per
  frame — shadow blur is the most expensive canvas operation, and at 240
  drones it is the first thing that will jank on a low-end phone. The
  standard fix is a pre-rendered radial-gradient glow sprite drawn with
  `drawImage()` instead of a shadow. Do it when the page gets real mobile
  traffic; do not do it casually, because it changes the glow's look.
- `thinUniform`'s fill loop is O(target × points × target) — bounded and
  fine at these sizes, but it is the reason the tight canvas matters: the
  loop's cost scales with the raster point count.
- Images are JPEG only, no `srcset` or AVIF/WebP. The 900 px cards are
  served to phones that display them at ~360 px. Add `srcset` with a
  480 w variant when the photos are replaced with real show photos.
- The `draw()` loop runs forever via `requestAnimationFrame` even after
  the formation settles. That is intentional (twinkle, starburst pulse,
  finale spin) and cheap at this dot count — leave it.

### 1.4 Idiomatic / DRY issues

**Fixed — contact email in 5 places.** `hello@whenwhere.biz` appeared in
the form sidebar, the footer, the config, and twice more as literal
strings. The README's checklist said "update it in the two places" —
wrong on both counts. Now `WHENWHERE_CONFIG.contactEmail` is the single
source: the two anchors carry `data-contact-email` and a 5-line sync at
load sets their `href` and text from the config. Change it there and
nowhere else.

**Fixed — fleet counts in 4 places.** `FLEET` (JS), the button labels
(HTML), the README table, and the package copy. The button labels are
now derived: each count sits in a `<span data-fleet="heart">80</span>`
and a sync after the initial formation fills it from `FLEET`. The README
table stays as documentation (that duplication is acceptable — it is a
human-readable spec, and the smoke test asserts the live values).

**Still duplicated, acceptable:** the 12 form fields exist in the HTML
form, in the `entries` map, and in the README's question list. The
`entries` map is the only one that must match Google exactly; the README
list is the procedure for producing it.

**Magic numbers.** The geometry is tunable constants with no names:
heart size 100, centers `.42/.58`, tilt `.18`, gap radius 30, crossing
thresholds 12/8/40, spin `0.15`, pulse `0.03`. They are fine as literals
in a single-purpose page, but the next person to tune the hearts will
have to reverse-engineer them from the code. The header comment in the
studio engine now explains the system; if the studio grows a sixth
shape, extract a `GEOMETRY` object with named fields.

## 2. Commenting & In-code Documentation

### Fixed — three stale comments that actively misled

- `fix_fleet`'s docstring and its call-site comment said words were
  "~15/character". The code is `chars.length * 25`. **Fixed to 25** in
  both places.
- The studio engine's header comment said words are "drawn one character
  at a time as outlines" — the code draws **filled** glyphs (the outline
  version was tried and reverted because it scattered the dots).
  **Rewritten.**
- The same comment said the hearts' "outlines cross twice" — the code
  now finds **every** crossing along the outline and alternates the
  under-heart at each one. **Rewritten** to describe the diagonal
  arrangement, the crossing detection, and why `resampleRuns()` exists
  (the old `resample()` interpolated dots across the weave gaps,
  quietly re-filling them — that bug is worth a comment, and now has one).

### What the code does well (keep it)

- `fix_fleet`, `fix_studio_shapes` (now removed), and
  `fix_studio_sampling` carry docstrings that explain the *why* with
  dates and the user-visible symptom ("a filled shape sampled on an 8px
  grid and thinned to 60–80 dots is a sparse cloud — the glass lost its
  bowl"). That is the right standard for this codebase.
- The `resampleRuns` comment states its invariant in one line ("never
  interpolates across a break").

### Still missing

- The form IIFE has no header comment explaining the demo-mode/configured
  split or the `no-cors` limitation — the two things a maintainer most
  needs to know before touching it. Add a 4-line comment at the top of
  the form IIFE.
- `setFormation`'s drone-reuse behavior (old drones morph from their
  current position, new ones rise from below the canvas) is the reason
  shape switches look smooth. One comment line would save the next reader
  a re-derivation.
- JSDoc is overkill for a single-file page, but the four pure geometry
  functions (`resample`, `resampleRuns`, `heartPair`, `wordPoints`)
  deserve `@param`/`@returns` lines — they are the unit-testable surface
  (see §3).

## 3. Future-Proofing & Architecture

### 3.1 The main issue: the repo cannot regenerate its own page

The build script reads a frozen upload (`tools/source.html`) and applies
~60 assertion-checked replacements. Step 1 of the migration below is
done (2026-11-12): the script and the upload now live in the repo, and
`.github/workflows/pages.yml` rebuilds the page on every push. The
remaining consequences are the patch-list ones:

- Every edit to the page must go through the patch list. The patch list
  is the de facto source of truth, but it is written as a sequence of
  string replacements — the hardest form to review, and the form that
  produced finding 1.2 (dead passes nobody noticed).
- The upload is a snapshot of a page that no longer exists anywhere else.
  If it is lost, the build cannot run at all.

**Recommended migration (in order):**

1. **Short term (no behavior change) — DONE 2026-11-12:**
   `whenwhere-drone-build.py` moved into the repo as `tools/build.py`
   and the upload checked in as `tools/source.html`. The repo is
   self-contained; the README's "rebuild" instructions are
   `python3 tools/build.py`, and the Pages workflow runs it on every
   push.
2. **Medium term:** invert the dependency — make `index.html` in the
   repo the source of truth, edited by hand, and shrink the build script
   to what a generator should do: optimize images, run the checks, and
   nothing else. The 60 string replacements are a record of a review,
   not a build system; keeping them forever means every future edit pays
   the anchor-matching tax.
3. **Long term:** extract the studio JavaScript into its own file
   (`studio.js`) so it can be linted, unit-tested, and given a real
   Content Security Policy (the page currently needs `unsafe-inline` for
   its inline script, so no CSP is possible as shipped).

### 3.2 Testing — added a smoke test; unit tests are the next step

There were no tests. **Added `tests/smoke.mjs`:** a dependency-free
Node script (built-in WebSocket client, Chrome over CDP) that loads the
built page, clicks every formation, and asserts the drone counts
(80/100/60/200/240), the word counts (LOVE 100, E + J 75, 2027 100), the
FLEET-derived button labels, and zero JS errors. It passes (verified in
this review). Run it with `node tests/smoke.mjs` after every rebuild.

What it does not cover, and should:

- **Unit tests for the pure geometry.** `heartPair`, `resampleRuns`,
  `wordPoints`, and `thinUniform` are pure functions of a target count
  and could be tested in Node with a minimal canvas stub. The highest
  value assertions: `resampleRuns` returns exactly `n` points with none
  inside a gap circle; `heartPair` finds ≥ 2 crossings; `wordPoints`
  returns exactly the target for a known string. Extracting them requires
  the `studio.js` split in §3.1 step 3 — that is the real reason to do
  the split.
- **CI.** A minimal GitHub Actions workflow (on push: run the build,
  run `node --check`, run the smoke test, fail the push if any step
  fails) would have caught every regression in this review's history
  before it shipped. The smoke test needs Chrome in the runner
  (`browser-actions/setup-chrome` or the Playwright image).

### 3.3 Configuration and versioning

- `WHENWHERE_CONFIG` inline in the page is the right call for a static
  site — do not move it to a separate file until there is a second page
  that needs it.
- There is no version anywhere: no version comment in the HTML, no
  `CHANGELOG.md`. Add a `<!-- v1.0.0 -->` comment and a short changelog
  (one line per shipped change, dated) so the deployed page can be traced
  to a build.
- The build has no `--check` mode and no `--help`. Add both when the
  script moves into the repo.

### 3.4 Coupling

- The studio, the form, and the package shortcuts are three IIFEs sharing
  the global `WHENWHERE_CONFIG` and a few element IDs. That is fine at
  this size. The coupling to watch is the form's dependence on the
  studio's `currentName` (the "Use this design" button reads a variable
  owned by another IIFE) — if the studio IIFE ever fails to load, the
  button throws. A one-line guard (`typeof currentName !== 'undefined'`)
  removes the coupling.
- The page depends on Google Fonts at runtime with no fallback beyond the
  `Georgia, serif` / `system-ui` stacks. Those fallbacks are correct and
  the page is readable without the fonts — verified by the `display=swap`
  URL parameter. Leave as is.

## 5. Visual Asset Strategy

Added five real assets under `docs/screenshots/` (all captured from the
built page in this review — no mockups):

| Asset | Depicts | Placed in README |
|---|---|---|
| `hero.png` (1280×900, 150 KB) | The hero section: headline, CTAs, festival-crowd photo | Directly under the title — the first thing a visitor sees |
| `formation-assembly.gif` (640×459, 380 KB) | The fleet assembling the interlocking hearts, 15 frames over ~3 s of real time | In Description, under the feature list — it is the page's signature interaction and a still cannot show it |
| `formation-hearts.png` (780×560) | Settled interlocking hearts (rose + gold, woven) | Gallery under the fleet table |
| `formation-finale.png` (780×560) | Settled grand finale (twin rings + 12 spikes, 240 drones) | Gallery under the fleet table |
| `formation-love.png` (780×560) | Settled "LOVE" (100 drones) | Gallery under the fleet table |

Why these, in this order: the hero establishes the product, the GIF
proves the studio is alive, and the three stills prove the three
hardest-won shapes (hearts, finale, words) read correctly at a glance.
The fleet table sits between the GIF and the stills so the numbers and
the pictures reinforce each other.

**How they were captured (reproducible):** stills are headless-Chrome
screenshots with `--force-prefers-reduced-motion` (snaps the fleet to its
final positions), cropped to the stage. The GIF cannot be captured that
way — the animation is `requestAnimationFrame`-driven and virtual time
does not fast-forward it — so `tests/capture-assembly.mjs` drives the
real browser over the DevTools Protocol, waits in real time, and shoots
a frame every 200 ms. The stitching command is in the README.

**Still to capture (needs real show photos, cannot be faked):**
